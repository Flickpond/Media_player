# Datastore review — before the first apply

**For:** whoever reviews the `terraform plan` that creates RDS and
ElastiCache (sprint 5, rule 7: someone other than the person applying).
**Why it needs a review:** since sprint 1, Postgres and Redis have listened
only on `127.0.0.1` (CLAUDE.md rule 2). With workers on other machines they
must be reachable over the network, and the API's per-user ownership checks
do not protect them: anything that reaches Postgres reads every user's data,
and anything that can write to the queue can make a worker run code of its
choosing (RQ jobs are serialised Python calls). A wrong rule here leaks
everything while the site keeps working, so it is checked before, not after.

## What opens

| | PostgreSQL | Valkey (the RQ queue) |
|---|---|---|
| Service | RDS `db.t4g.micro`, Postgres 16 | ElastiCache `cache.t4g.micro`, Valkey 8 |
| Port | 5432 | 6379 |
| Admitted from | the core's security group (`flickpond-<env>-app`); the worker group's, added by `infra/workers` | the same two, nothing else |
| Public address | none (`publicly_accessible = false`) | impossible — ElastiCache has no public endpoint |
| In transit | TLS required: `rds.force_ssl = 1` refuses plain connections; the DSN carries `?ssl=require` | TLS (`transit_encryption_enabled`); the client uses `REDIS_SSL=true` |
| Authentication | user `flickpond`, 40-character generated password | 48-character generated auth token |
| At rest | encrypted (`storage_encrypted`) | encrypted (`at_rest_encryption_enabled`) |
| Backups | daily, kept 7 days, point-in-time restore | none on purpose: the reaper rebuilds the queue from Postgres |
| Deletion | protected unless `protect_data = false` (staging only) | — |

**Secrets** are generated by Terraform and written only to SSM Parameter
Store as `SecureString`: `/flickpond/<env>/postgres_dsn` and
`/flickpond/<env>/redis_password`. Readable by the app role for that
environment only. Never a Terraform output, never committed, never pasted
into chat. They are in the Terraform state, which is why the state bucket is
private, encrypted, versioned and locked (`infra/bootstrap`).

## What the reviewer checks in the plan

- [ ] Every new ingress rule on `…-db` and `…-cache` names a
      **`referenced_security_group_id`**, never a `cidr_ipv4`. Search the plan
      for `0.0.0.0/0` — it may appear only on the core's 80/443 and egress.
- [ ] `publicly_accessible = false` on the RDS instance.
- [ ] `transit_encryption_enabled = true` and an `auth_token` (shown as
      sensitive) on the replication group.
- [ ] The parameter group sets `rds.force_ssl = 1`.
- [ ] `protect_data` is `true` for production.
- [ ] No secret value appears in the plan's output section (only the
      parameter **names**).

## Proving it after the apply — tested, not assumed

From **outside AWS** (any laptop), both must fail to connect:

```bash
nc -vz -w 5 <db_endpoint> 5432       # times out: no public address
nc -vz -w 5 <cache_endpoint> 6379    # does not even resolve publicly
```

From the **core host**, both must succeed — and Postgres must refuse a
plain-text connection:

```bash
DSN=$(aws ssm get-parameter --with-decryption --name /flickpond/staging/postgres_dsn --query Parameter.Value --output text)
psql "${DSN/\?ssl=require/?sslmode=require}" -c 'select 1'        # works
psql "${DSN/\?ssl=require/?sslmode=disable}" -c 'select 1'        # refused: no encryption
```

And from the **core host with the worker group not yet attached**, the
worker security group has no rule yet, so only the core is admitted until
`infra/workers` is applied — that apply is reviewed the same way.

Record the results in the PR that applies it.

## If something is wrong

Remove the offending rule (or `terraform destroy -target` the rule), then
rotate the exposed secret: `terraform apply -replace=random_password.db`
(or `.cache`) regenerates it and rewrites the SSM parameter; restart the
API, reaper and workers so they read the new one.
